## 用 Hermes 打通官网到 GitHub 的自动同步：一次完整的工程化实践复盘

先问你个问题：如果你有一个内容网站，每天要发文章，还要同步到多个平台做 SEO 和 AI 收录，你会怎么做？

手动复制粘贴？那太慢了。脚本定时跑？得自己写一堆代码。今天我想跟你分享的，是我和 Hermes 一起摸索出来的一套方案——**用 AI 智能体做"中枢"，把官网、GitHub、Dev.to 三个平台自动串成一条流水线。**

这篇文章不空谈概念，只讲真实的背景、规划、实施和踩过的坑。如果你也想做类似的自动化，可以直接照着思路落地。

### 一、背景：为什么一定要打通？

先说说动机。我做内容平台，靠的是"内容 → 搜索引擎/AI 收录 → 引流到官网"这套逻辑。这里有个很现实的问题：

- **搜索引擎收录**：内容发到多个平台，能增加曝光和被收录的概率。

- **AI 收录（AEO）**：现在越来越多人在用 AI 检索，而 GitHub 这类技术平台是 AI 训练的高权重来源。

- **效率**：如果每篇文章都要手动复制到各个平台，工作量会压垮人。

所以我的目标是：**在官网发一篇文章，自动同步到 GitHub（作为 AI 收录和 SEO 外链），最好还能发到 Dev.to（开发者社区，AI 抓取率高）。**

### 二、技术选型：为什么用 Hermes 当"中枢"？

一开始我考虑过几种方案：

- **n8n 低代码**：要搭额外服务，配置复杂，且要一直跑着。

- **自写脚本**：能做，但每次改需求都要动代码，维护麻烦。

- **Hermes 智能体**：既能写脚本，又能理解业务逻辑（比如过滤付费内容、处理格式），还能定时执行。

最终我选了 **Hermes + 脚本** 的组合：Hermes 负责理解业务、生成和调度脚本，脚本负责确定性的同步动作。这样既灵活，又稳定。

### 三、整体架构：一条流水线

整个系统的核心是一条流水线：

**官网发布文章 → Hermes 读取 → 过滤付费内容 → 转 Markdown → 推送 GitHub → 回填链接 →（可选）发布 Dev.to**

拆开来看，有几个关键环节：

- **数据源**：通过 WordPress REST API 读取文章（用 Basic Auth）。

- **内容处理**：把 HTML 转成 Markdown，并对付费内容做特殊处理。

- **分发**：调用 GitHub API 上传文件，调用 Dev.to API 发文章。

- **回填**：把同步好的外链，写回官网文章的"全网发布"模块。

- **调度**：用 cron 定时任务每天自动跑，也可以手动触发。

### 四、核心实现：几个关键技术点

这里挑几个最关键的实现细节，都是有实操价值的：

**1. 读取文章（WordPress REST API）**

用 Basic Auth 读取文章的原始内容（含 HTML 标签），这是处理的第一步。

GET /wp-json/wp/v2/posts/{id}?context=edit

**2. HTML 转 Markdown**

写一个转换函数，把标题、段落、加粗、列表等 HTML 转成 Markdown。这一步是为了让 GitHub / Dev.to 能正确渲染，也利于 AI 爬虫解析。

**3. 上传 GitHub（创建或更新）**

用 GitHub 的 Contents API：上传文件用 PUT，如果文件已存在，需要先拿到当前 sha 再更新（否则报错）。

PUT /repos/{org}/{repo}/contents/{path}
body: { message, content(base64), sha(更新时需要) }

**4. 回填链接（更新官网全网发布模块）**

同步完 GitHub 后，把 GitHub 链接回填到官网文章的"全网发布"模块。这里有个关键点——**更新文章时不能只传 title/content，否则会清空特色图片、分类、标签**。必须先读取原字段，再合并更新。

### 五、踩过的坑（全是真实教训）

整个过程中踩了不少坑，我挑几个最有代表性的：

**坑1：WAF 拦截 print (**

往官网提交含 Python 代码的文章时，遇到 403 Forbidden。排查了很久，发现是 **代码里的 print ( 被 WordPress 的 WAF（防火墙）误判为代码注入**。解法是把它改成 print (（加空格），功能不变，绕过拦截。

**坑2：长内容分段更新**

文章太长时，一次性提交会被拒。解法是**分段更新**：每次只提交前缀，循环增长，直到完整内容写进去。

**坑3：付费内容泄露**

官网有部分文章是付费才能看全文的（用 Erphpdown 插件的 [此处为付费内容，官网查看] 标记）。如果直接同步到 GitHub，就会把付费内容免费泄露。所以同步前**必须过滤付费内容**，只同步公开部分。

**坑4：Dev.to 限流**

Dev.to 对新账号有严格的频率限制（429 Too Many Requests，一次要等 300 秒）。批量发布时要做好重试和分批，不能一股脑全发。

**坑5：canonical 链接**

同步到 GitHub/Dev.to 的文章，必须填写 canonical_url 指向官网原文（单篇链接，不是首页），否则搜索引擎会判定为重复内容，反而降权。

### 六、效果与价值

这套体系跑通后，带来的价值是实实在在的：

- **效率**：从"每篇手动同步"变成"自动流水线"，省下大量时间。

- **SEO 外链**：GitHub、Dev.to 成为内容的权威外链来源。

- **AI 收录**：GitHub 是 AI 训练的高权重来源，内容更容易被 AI 检索到。

- **品牌一致**：多平台统一品牌、统一来源，强化"道道量化·1848"的辨识度。

这次实践给我最大的体会是：**AI 智能体 + 确定性脚本，是一种很实用的自动化组合。**AI 负责理解和调度，脚本负责稳定执行，各司其职。

更重要的是，这套体系不是一次性的，它让"内容生产 → 多平台分发 → SEO/AI 收录"变成了一条可持续运转的流水线。以上是我的一点实践分享，也欢迎交流探讨。

### 常见问题（FAQ）

#### 问：用 Hermes 做同步，难不难？

不难。核心是让 Hermes 帮你生成和调度脚本，你不用自己写很复杂的代码。关键是把流程想清楚：读数据、处理、分发、回填。

#### 问：付费内容怎么保证不泄露？

同步前必须检测并过滤付费标记（如 Erphpdown 的标签），只同步公开部分。这个逻辑要写死在脚本里，是底线。

#### 问：为什么要填 canonical 链接？

告诉搜索引擎"原文在我官网，其他平台只是转载"，防止重复内容被降权。这是 SEO 的关键，一定要填单篇原文链接，不是首页。
